# 숙소명 입력형 릴스 대본 엔진

이 문서는 Moodstay의 대본 생성 기준이다. 사용자가 숙소 이름만 말해도 이 흐름을 그대로 실행한다. 핵심 목표는 시설 안내가 아니라 **첫 장면에서 시선을 잡고, 숙소 이름을 궁금하게 만들고, 끝까지 보게 하는 판매형 경험담**이다.

## 입력과 기본 출력

- 입력: 숙소 이름 하나. 사용자가 별도 방향을 주면 그 지시를 우선한다.
- 조사: 공개 웹에서 현재 공식 정보와 후기·방문 콘텐츠를 확인한다. 공식 페이지만 고집하지 않되, 서로 다른 출처에서 사실을 맞춘다.
- 출력: 이름을 감춘 Typecast용 한국어 내레이션 대본 한 편.
- 기본 길이: 대략 20~30초 분량을 목표로 하되, 말이 부자연스럽게 압축되거나 늘어나면 자연스러움을 우선한다. 실제 길이는 Typecast 음성으로 최종 확인한다.
- 설명이나 근거를 덧붙일 때는 대본 바깥에 짧게 둔다. 대본 안에 URL, 출처, 메모, 컷 번호를 섞지 않는다.

## 생성 절차

### 1. 사실과 장면을 빠르게 조사한다

숙소의 위치·객실 콘셉트·실제 이용 가능한 시설·체험·식음·시즌 정보를 확인한다. 출처별로 서로 다른 점은 보류하고 단정하지 않는다. 현재 운영 여부가 바뀔 수 있는 수영장, 프로그램, 가격, 패키지는 최신 자료를 우선한다.

조사 메모에서 다음을 고른다.

- 가장 강하게 보여줄 수 있는 시각적 한 장면
- 다른 숙소와 구별되는 한 가지 의외성
- 그 장면이 시청자에게 주는 실용적·감정적 보상
- 낮부터 밤까지 이어지는 체류 경험

시설을 많이 채우는 것이 목표가 아니다. 화면으로 증명할 수 있고, 이야기의 재미를 키우는 사실만 사용한다.

### 2. 세 레퍼런스 구조 중 하나를 고른다

모든 대본을 똑같은 틀에 억지로 끼우지 않는다.

1. **장면형 훅 → 혜택 누적 → 만족 결말**
   예: 잠에서 깨자마자 특별한 풍경이 보임 → 장비/체험/먹거리 → 하루를 잘 보냈다는 감상.
2. **정체 반전 → 몰입 장면 → 가치 결론**
   예: 한국인데 다른 나라 같은 공간 → 날씨·온천 등 구체적 순간 → 여행지로서의 만족.
3. **공감되는 욕구/갈등 → 발견 경위 → 문제 해결 → 만족 결말**
   예: 동행자와 원하는 여행이 다름 → 지인의 추천으로 발견 → 둘 다 즐길 요소 → 함께 만족.

숙소의 시설·위치·가격·포함 혜택·계절 운영은 실제 근거가 확인되는 것만 쓴다. 계정 주인은 가상의 여행 페르소나이므로 주관적인 발견과 반응은 이야기로 구성할 수 있지만, 부부 갈등·친구 추천·회사에서 들은 정보 같은 개인사를 매번 억지로 붙이지 않는다. 사용자의 레퍼런스나 선택한 훅에 실제로 도움이 될 때만 쓰며, 검증되지 않은 숙소 사실을 암시하거나 대체해서는 안 된다.

### 3. 내레이션을 이야기로 쓴다

기본 흐름은 다음과 같다.

1. **첫 문장 훅:** 구체적이고 눈앞에 장면이 그려지는 의외성으로 시작한다. “오늘 소개할 숙소는…”이나 “제주 숙소 추천” 같은 일반 소개는 금지한다.
2. **발견/기대:** 왜 특별한지 한두 문장으로 연결한다. 정보만 나열하지 말고 시청자가 그 공간에 들어가는 순서대로 쓴다.
3. **체류 경험:** 객실의 분위기와 실제 즐길 일을 낮–저녁–밤처럼 이어준다. 특징마다 시청자에게 돌아오는 편안함·재미·편리함을 보여준다.
4. **엔딩:** 앞에서 쌓은 기대를 개인적인 만족감이나 추천 이유로 닫는다. 질문이나 댓글 요청으로 끝내지 않는다.

문장 리듬은 “-인데요”, “-더라고요”, “-니까”, “-까지”처럼 자연스러운 구어체를 쓴다. Typecast가 읽기 쉽게 한 문장에 한 호흡만 담는다. 시설 목록, 보도자료 말투, 과장된 최상급 표현은 피한다.

화자는 여행을 많이 다녀본 20대 여성의 1인칭 방문 경험이다. 근거 없이 당일치기나 숙박 일수를 정하지 않고, 동행자·갈등·지인 추천도 훅에 꼭 필요하지 않으면 만들지 않는다. `A프레임` 같은 제작자 용어보다 `삼각 숙소`, `오두막`처럼 시청자가 바로 이해하는 말을 쓴다. 화면 자막을 짧게 나누더라도 TTS 문장 자체는 끊기지 않는 자연스러운 전체 문장으로 먼저 완성한다.

### 4. 댓글을 부르는 미공개 규칙을 지킨다

- 숙소 정식명·브랜드명·정확한 지점을 **대본/내레이션/화면 자막에서 공개하지 않는다.** 숙소 이름은 프로젝트 제목, 조사 메모 등 내부 식별용으로만 쓸 수 있다.
- 이름을 감추는 것이 궁금증 장치다. 따라서 대본에 댓글 행동을 직접 지시하는 문구를 추가하지 않는다.
- 다음 류의 결말은 금지한다: “여기 어딘지 궁금하면 댓글로 물어봐요”, “댓글에 정보 남겨주세요”, “댓글 달면 보내드릴게요”, “DM 주세요”.
- 계정 운영자가 나중에 댓글/DM 문구를 요청하면, 내레이션과 분리된 운영 문구로 작성한다.

### 5. 최종 검수

내보내기 전에 확인한다.

- 첫 문장만 들어도 다음 장면이 궁금한가?
- 특이점이 실제 숙소 정보와 일치하고, 영상 이미지로 보여줄 수 있는가?
- 중간이 시설 나열이 아니라 체류 경험의 흐름인가?
- 엔딩이 만족감/추천 감정으로 마무리되는가?
- 대본 어디에도 숙소 이름이나 직접 댓글 CTA가 없는가?
- 확인하지 못한 가격·포함 혜택·운영 시간·개인 체험을 사실처럼 쓴 곳이 없는가?
- Typecast에 그대로 붙여넣을 수 있는가?

`tools/validate_script.py`는 마지막 두 가지 브랜드 규칙(숙소명 노출, 직접 댓글 CTA)과 경험형 비질문 엔딩을 자동 점검한다. 자동 검사는 사실 검증이나 대본 품질 판단을 대체하지 않는다.

## 사용자가 받는 기본 응답 형태

숙소명이 포함된 작은 작업 제목 다음에, TTS로 읽을 문장만 별도 블록으로 제공한다. 대본 안에는 숙소 이름을 쓰지 않는다. 웹에서 사실을 확인했다면 출처 링크는 대본 바깥에 간단히 표시할 수 있다. 사용자가 요청하지 않은 분석표·컷 구성·댓글 유도문은 덧붙이지 않는다.
